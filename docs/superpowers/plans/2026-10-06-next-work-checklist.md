> Agent 실행 시 `executing-plans`로 이 문서를 단계별로 진행한다. Tester와 Reviewer는 가능한 한 별도 컨텍스트에서 검증한다. 체크박스는 실제 근거가 확보된 뒤 갱신한다.

**기술:** Python, nanobot submodule, SQLite, Telegram, Linux/systemd.

**기준 문서:** [구현 로드맵](../../implementation-roadmap.md), [개발 워크플로우](../../development/agentic-workflow.md), [공통 운영 절차](../../development/operations-runbook.md).

## 사용 방법

1. 아래의 **현재 다음 작업 T1**부터 시작한다.
2. 작업 시작 시 연결 Issue·PR의 최신 상태를 다시 확인한다.
3. 각 작업의 산출물과 완료 조건이 충족되면 근거 링크를 붙이고 체크한다.
4. 사용자 승인 메시지와 승인 범위는 해당 Issue/PR에 기록한다.
5. 완료·보류 결과를 이 문서에 반영하고 다음 작업으로 이동한다.

이 문서 작성은 새 Issue 생성·Ready 전환·서버 변경·병합 승인을 뜻하지 않는다.
로드맵의 후보와 아래 작업 ID는 실제 Issue 번호가 아니다.
실제 서버·SSH 별칭·사용자·절대 경로는 비공개 `.env`와 운영 기록에서만 관리한다.

## T1. 0단계 잔여 검증 범위와 계획

**지금 할 일:** 후속 Planning Issue를 준비한다. 기존 OCI 백업 증거를 재사용할 수 있는 범위와 새 실행이 필요한 범위를 구분한다.

- [ ] 로드맵의 0단계 항목을 `문서 완료 / OCI 실행 완료 / 미검증`으로 분리한 검증표를 작성한다.
- [ ] 후보 업데이트·smoke·복귀 검증의 대상 버전과 방법을 제안한다. 현재 main 문서 반영만을 위해 런타임 배포가 필요한지부터 판단한다.
- [ ] Telegram 실제 응답, 뉴스 생성과 실제 수신, tracking 저장·알림 등 smoke의 구체적인 확인 항목을 정한다.
- [ ] 코드 복귀와 데이터 복귀를 구분한다. 운영 DB 교체를 동반하는 연습은 별도 승인 범위를 명시하고, 우선 격리 환경에서 연습할 방법을 제안한다.
- [ ] RPi 검증 대상의 준비 여부를 확인한다. 대상이 없으면 RPi를 BLOCKED로 유지하고 OCI 결과를 두 플랫폼 PASS로 표시하지 않는다.
- [ ] 중단 예산, 백업의 유효 시점, 발송·API 비용, 실패 시 복귀, 실제 데이터 영향과 실사용 관찰 기간을 Issue 본문에 정한다.
- [ ] Human 설계 승인과 Ready 전환 근거를 확보한다.
- [ ] 실행 직전 읽기 전용 점검을 완료하고 구체적인 대상·버전·작업창·영향을 승인받는다.
- [ ] 승인 범위에서 검증하고 현재 SHA의 독립 Test/Review 보고서와 PR을 작성한다.
- [ ] Human 결과 수용·명시적 병합 승인 후 완료 상태와 로드맵을 갱신한다.

**산출물:** Planning Issue → 실행 승인 기록 → 비공개 운영 기록 → 공개 검증 보고서/PR.

**완료 조건:** 각 잔여 검증의 실제 결과와 제한이 기록되고, 아직 막힌 항목을 통과로 처리하지 않았다. T2·T3 착수에 필요한 운영 전제와 제한을 Human이 수용했다.

## 작업마다 적용할 완료 체크

- [ ] Issue 본문의 승인 설계와 AC를 확인했다. AC는 결과를 수용할 기준이다.
- [ ] 상태 라벨이 정확히 하나이며 Ready 승인 근거가 있다.
- [ ] 기존 PR·브랜치를 재사용하거나 Issue별 격리 브랜치를 만들었다.
- [ ] 현재 SHA에서 관련 검증과 독립 Tester/Reviewer 결과를 확보했다.
- [ ] PR에 Issue·승인·명령·종료 코드·AC 근거·제약을 기록했다.
- [ ] 필요한 운영 검증은 대상·범위 승인을 받은 뒤 수행했다. 적용되지 않는 배포·실사용은 Human이 N/A 근거를 수용했다.
- [ ] Human PR 검토·결과 수용·명시적 병합 승인이 있다.
- [ ] Merge·Issue 종료와 최종 코드/운영 버전 관계를 확인했다.

결과 양식은 [검증 보고서 템플릿](../../development/verification-report-template.md), 비공개 운영 값은 [운영 기록 양식](../../development/private-operations-record-template.md)을 사용한다.
새 문제는 Open Issue로 기록하고, 이 문서의 체크를 대신해 승인이나 PASS를 만들지 않는다.
