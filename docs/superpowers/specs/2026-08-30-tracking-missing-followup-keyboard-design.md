# 저장 후 미기록 후속 질문과 키보드 설계

## 목표

생활 기록을 저장한 뒤 기존의 저장 결과와 통계 조언을 먼저 응답하고, 최근 기록 중 비어 있는 항목이 있으면 가장 최근 항목 하나를 추가로 질문한다. Telegram에서는 질문 대상의 스키마에 맞는 reply keyboard도 함께 표시한다.

예시 흐름:

1. 봇이 오늘 수면 시간을 묻는다.
2. 사용자가 `6시간`이라고 답한다.
3. 봇이 수면 저장 결과와 최근 기록 조언을 응답한다.
4. 전날 영어공부 기록이 비어 있으면 `어제 영어공부 기록이 비어 있어. 영어공부 했어?`라고 이어서 묻고 `했어`, `안 했어` 버튼을 표시한다.

## 범위와 규칙

- 검색 범위는 방금 저장한 `recorded_for` 날짜 이전 7일이다. 방금 저장한 날짜 자체는 검사하지 않아 아직 예정 시각이 오지 않은 당일 항목을 성급하게 묻지 않는다.
- 날짜는 최신순으로 검사한다. 같은 날짜에 여러 항목이 비어 있으면 추적 항목의 기존 목록 순서를 사용해 하나만 선택한다.
- 저장한 항목과 다른 항목도 후보가 될 수 있다.
- 값이 `false` 또는 `0`인 기록은 유효한 응답이며 미기록으로 취급하지 않는다. 해당 날짜의 DB 행이 없을 때만 미기록이다.
- 미기록이 없으면 저장 결과와 조언만 보내고 키보드를 제거한다.
- 한 응답에서 후속 질문은 최대 하나만 한다. 사용자의 다음 답변을 저장하면 같은 절차가 다시 실행되어 다음 미기록을 순차적으로 채운다.
- 추적 항목 삭제, 조회, 통계, 최초 알림과 정기 retry 동작은 변경하지 않는다.

## 구성 요소

### RecordManager

`RecordManager`에 기준일 이전 최근 7일을 검사해 다음 미기록 후보를 반환하는 메서드를 추가한다. 반환값에는 항목 정보와 `recorded_for`가 포함된다. 조회는 기존 `Storage.record_exists()`와 `TrackedItemManager.list_all()`을 사용하며 DB 스키마는 바꾸지 않는다.

질문 문구와 키보드는 dispatcher가 이미 사용하는 스키마별 포맷 함수를 재사용한다. 이를 위해 dispatcher의 단일 항목 질문/키보드 생성 기능을 외부에서도 사용할 수 있는 작은 공개 함수로 정리한다.

### tracking CLI

`tracking record`가 저장과 조언 출력을 마친 뒤 미기록 후보를 조회한다. 후보가 있으면 에이전트가 안정적으로 해석할 수 있는 JSON 한 줄을 추가 출력한다. 이 JSON에는 후속 질문 텍스트와 2차원 버튼 배열만 담으며, 사용자에게 그대로 노출하지 않는다.

예시 개념:

```json
{"follow_up_question":"어제 영어공부 기록이 비어 있어. 영어공부 했어?","reply_keyboard":[["영어공부 2026-08-29 했어","영어공부 2026-08-29 안 했어"]]}
```

### MessageTool과 OutboundMessage

메시지 전송 도구에 선택적 `reply_keyboard: list[list[str]]` 입력을 추가한다. 값이 있으면 `OutboundMessage.metadata["reply_keyboard"]`로 전달한다. 기존 호출자는 이 필드를 생략하므로 인터페이스 호환성을 유지한다.

tracking 스킬은 기록 저장이 성공할 때마다 다음을 수행하도록 안내한다.

1. 저장 결과와 조언을 자연어로 정리한다.
2. 후속 질문이 있으면 마지막에 붙인다.
3. 최종 텍스트와 `reply_keyboard`를 메시지 전송 도구로 한 번에 보낸다. 후속 질문이 없으면 빈 배열을 전달해 이전 키보드를 제거한다.
4. JSON과 전체 CLI 명령은 사용자에게 노출하지 않는다.

메시지 전송 도구가 현재 대화에 직접 메시지를 보내면 기존 `_sent_in_turn` 동작이 일반 최종 응답의 중복 전송을 막는다.

### Telegram 채널

Telegram 채널은 `OutboundMessage.metadata["reply_keyboard"]`를 읽어 `ReplyKeyboardMarkup`으로 변환한다. 키보드는 마지막 텍스트 청크에만 붙인다. 긴 응답이 여러 메시지로 나뉘어도 질문과 버튼이 함께 도착하도록 하기 위함이다.

키보드 값이 명시적으로 빈 배열이면 `ReplyKeyboardRemove`를 사용한다. 필드 자체가 없으면 기존 메시지 동작을 그대로 유지하여 일반 응답이 기존 키보드 상태를 의도치 않게 바꾸지 않도록 한다.

HTML 렌더링 실패로 일반 텍스트를 재전송할 때도 같은 reply markup을 유지한다.

## 데이터 흐름

1. 사용자의 기록 답변을 받은 에이전트가 `tracking record` CLI를 실행한다.
2. CLI가 DB에 기록을 upsert하고 기존 조언을 생성한다.
3. CLI가 기준일 이전 7일에서 가장 최근 미기록 한 건을 선택한다.
4. 미기록이 있으면 질문과 키보드 JSON을 CLI 출력에 추가한다.
5. tracking 스킬 지침에 따라 에이전트가 저장 결과, 조언, 질문을 합쳐 메시지 전송 도구를 호출한다.
6. 메시지 전송 도구가 키보드를 outbound metadata에 넣는다.
7. Telegram 채널이 최종 텍스트와 reply keyboard를 함께 전송한다.
8. 사용자가 버튼을 누르면 날짜와 항목명이 포함된 기존 버튼 답변 처리 규칙에 따라 다음 기록이 저장된다.

## 실패 처리

- 기록 저장이 실패하면 현재 규칙대로 오류를 그대로 알리고 후속 질문이나 키보드를 만들지 않는다.
- 미기록 조회 또는 후속 질문 생성이 실패하면 저장 성공 자체를 되돌리지 않는다. CLI는 저장 성공 뒤 후속 처리 경고를 출력하여 저장 여부와 후속 처리 실패를 구분할 수 있게 한다.
- 잘못된 `reply_keyboard` 구조는 메시지 전송 도구에서 오류로 반환하며 Telegram API로 보내지 않는다.
- Telegram 전송 재시도와 HTML fallback은 기존 정책을 유지하며 reply markup도 보존한다.
- Telegram 이외 채널은 metadata를 무시하고 텍스트 질문만 전달할 수 있다.

## 테스트

- `RecordManager`: 기준일 제외, 최근 7일 경계, 최신 날짜 우선, 같은 날짜 항목 순서, `false`와 `0`을 기록으로 인정, 미기록 없음.
- dispatcher 포맷: duration, boolean, quantity, freetext 질문과 키보드가 기존 알림과 동일함.
- tracking CLI: 저장 결과와 조언 뒤에 후속 JSON 출력, 후보가 없을 때 JSON 미출력.
- MessageTool: 키보드 입력 검증과 outbound metadata 전달, 기존 키보드 없는 호출 호환성.
- Telegram 채널: 마지막 청크에만 `ReplyKeyboardMarkup` 적용, 빈 배열일 때 제거, HTML fallback에서도 유지.
- 통합 성격 테스트: 오늘 수면을 저장한 뒤 전날 영어공부가 비어 있으면 영어공부 질문과 boolean 키보드가 생성됨.

## 비목표

- 한 번에 여러 미기록 질문을 묶어 보내기
- 사용자별 검색 기간 설정
- DB 마이그레이션 또는 새로운 pending 테이블 추가
- 정기 dispatcher의 retry 정책 변경
- Telegram 인라인 키보드 도입
