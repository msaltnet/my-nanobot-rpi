# 프로젝트 방향에 따른 구현 로드맵

기준일: 2026-10-05. [주요 기능과 프로젝트 방향](project-direction.md)을 실제 개발 순서로 나눈다.
목표는 **중요한 변화를 먼저 알려주고, 누적 생활 기록을 돌아보도록 돕는 개인 비서**다.

현재 뉴스 브리핑·조회, 생활 기록·통계·패턴 코멘트, 능동 질문은 코드에 있다.
Watch와 정기 Review는 새 개발 영역이다. 기존 기능을 다시 만들지 않고 운영 근거를 확인한 뒤 확장한다.
단계 0~6은 작업 순서이며 GitHub Projects에 추가할 상태가 아니다.
아래 체크리스트는 앞으로 할 일이고, Issue 후보 ID는 실제 GitHub Issue 번호가 아니다.

## 공개 프로젝트의 배포 원칙

RPi와 OCI Cloud Instance를 모두 지원하는 단일 Linux 호스트 구조를 유지한다.
특정 운영자의 서버·SSH 별칭·사용자명·설치 경로·실행 중인 버전을 제품 요구사항으로 고정하지 않는다.
공개 문서는 요구 버전, 환경 설정 방법, 경로 선택 규칙, 서비스·타이머 설치와 검증·복구 절차를 제공한다.
실제 배포 버전·경로·서버 상태는 각 운영자가 자신의 환경에서 점검하고 비공개 운영 기록으로 관리한다.
프로젝트 기여용 Projects 보드와 Human Gate는 개발 절차이며, 앱을 설치하는 사용자에게 보드 참여를 요구하지 않는다.

## 전체 순서

| 단계 | 사용자 / 운영 목표 | 우선 산출물 | 선행 조건 |
|------|---------------------|-------------|-----------|
| 0. 개발·운영 준비 | 검증과 복구가 가능한 개발 시작 | 연결된 보드·운영 기준·백업/복구 절차 | 준비된 워크플로우 문서 검토 |
| 1. 기존 기능 안정화 | 브리핑과 기록을 믿고 사용 | 현재 기능 검증표·필요한 수정 PR | 단계 0 |
| 2. Watch 관리 | 관심 조건을 등록·조회·끄기 | Watch 관리 CLI·Telegram UX·저장소 | 단계 1, Watch 설계 승인 |
| 3. Watch 알림 | 새 기사 중 중요한 변화만 받기 | 평가·중복 방지·발송·운영 보고 | 단계 2, 독립 수집·발송 설계 승인 |
| 4. 생활 Review | 일주일 생활 기록을 돌아보기 | 근거 있는 생활 요약·정기 전송 | 단계 1, 기간 집계 기준 승인 |
| 5. 통합 Review | 관심 정보와 생활을 한 번에 돌아보기 | 뉴스·Watch·생활 통합 주간 보고 | 단계 3·4 |
| 6. 실사용 개선 | 계속 쓰고 싶은 개인 비서 | 근거 기반 개선 Issue·회고 | 이전 단계들의 실제 사용 기록 |

권장 실행은 표 순서다. 단계 4는 Watch와 기술적으로 독립적이므로 사용자 가치에 따라 단계 2~3보다 먼저 할 수 있다.
실제 착수 순서는 Human이 승인한 Ready Issue로 확정한다. 일정·완료 날짜는 Issue 범위와 검증 환경을 정한 뒤 산정한다.

## 모든 구현에 적용할 완료 절차

각 Issue는 Open → Planning → **Human 설계 승인** → Ready 이후에 구현한다.
코드·테스트 → 독립 Tester → 독립 Reviewer가 현재 SHA에서 PASS하면 PR을 만든다.
승인된 후보 배포·smoke → Human 실사용·PR 검토 → 최종 수용 → Merge·Issue Close·운영 버전 확인 순서로 완료한다.
전체 단계가 끝날 때까지 기다리지 않고 **작은 Issue/PR 단위로** 이 절차를 반복한다.

운영 배포는 범위·후보 SHA·데이터 영향·롤백을 Human이 승인한 뒤 실행한다.
CI PASS만으로 배포·실사용 완료나 Merge 승인을 대신하지 않는다.
세부 규칙과 보고서 형식은 [개발 워크플로우](development/agentic-workflow.md)를 따른다.

## 단계 0. 개발과 운영 기준 확보

**목적:** 개발 Agent가 승인된 작업을 찾고, 운영 후보를 안전하게 검수할 수 있게 한다.

해야 할 일:

- [ ] 현재 준비된 AGENTS·Issue/PR 템플릿·개발 가이드를 검토하고 기본 브랜치에 반영한다.
- [ ] Projects 권한과 보드 URL을 확보하고 Open / Planning / Ready for Implementation 세 Status를 적용한다. Done 자동 전환을 끈다.
- [ ] RPi/OCI 공통 운영 요구사항과 점검 방법을 문서화한다: 코드 버전 확인, Python·nanobot 호환 버전, 서비스·타이머 설치, DB·워크스페이스 경로 선택·확인 절차. 실제 값은 운영자별 비공개 기록으로 관리한다.
- [ ] RPi와 OCI 각각의 설치·기동·업데이트·smoke 절차를 제공하고, 사용자명·설치 위치·SSH 연결을 환경에 맞게 지정할 수 있도록 한다.
- [ ] SQLite·설정·워크스페이스의 일관된 백업 및 복구 절차를 만들고 운영 데이터와 분리된 환경에서 복구를 확인한다.
- [ ] RPi 또는 OCI에서 운영자가 선택한 후보 배포 대상과 방식, Telegram 중복 연결·발송 방지, smoke 절차, 장애 시 이전 버전 복귀를 정한다. 특정 서버 접근을 기여·설치의 전제 조건으로 삼지 않는다.
- [ ] 공통 관찰 항목을 정한다: 수집·브리핑 성공, 기록 성공, 알림 중복·누락, API 실패, 메모리·디스크, 호출 비용의 확인 가능 범위.

**산출물:** 기여용 보드 설정, RPi/OCI 공통 요구사항·환경별 설치 가이드, 운영자가 사용할 비공개 점검 기록 형식, 백업/복구·후보 배포 절차, 관찰 기준.

**완료 조건:** Ready Issue를 조회할 수 있고, 후보 SHA를 배포·검수·복구할 방법을 확인했다.
RPi/OCI 모두에 적용 가능한 절차와 환경 차이를 확인하고, 실제 검증한 환경과 미검증 환경을 구분한다.
개별 운영자의 보드 권한·서버 준비 상황을 공개 제품의 완료 조건으로 쓰지 않는다. 배포 준비 문서만으로 복구 검증을 통과했다고 기록하지 않는다.

**Issue 후보:** `R0 운영 기준·백업·후보 배포 절차 확립`. 보드 설정은 개발 환경 준비 작업으로 별도 추적한다.

진행 기록(2026-10-05): [R0 Issue #2](https://github.com/msaltnet/my-nanobot-rpi/issues/2)에
문서 범위 설계와 Human 승인 근거를 기록했다. [공통 운영 절차](development/operations-runbook.md)와
[비공개 운영 기록 양식](development/private-operations-record-template.md)을 준비했다.
Projects 상태·자동화는 권한 부족으로 미확인이며, RPi/OCI 실제 설치·기동·백업/복구·후보 배포는
미수행이다. 따라서 위 체크리스트와 0단계 완료 상태는 그대로 유지한다.

## 단계 1. 기존 뉴스·생활 기록 안정화

**목적:** 확장 전에 기존 비서의 기본 경험을 검증하고, 발견한 문제만 수정한다.

뉴스에서 할 일:

- [ ] 소스별 성공·실패와 기사의 발행 시각·원문 URL·중복 처리를 점검한다. 한 경로 실패가 다른 경로를 중단시키지 않는지 확인한다.
- [ ] 07:00·14:00·20:00 브리핑의 실행·생성·Telegram 수신을 구분해 확인한다.
- [ ] 빈 수집 결과, 오래된 기사, 이미 브리핑한 기사, LLM 실패, Telegram 발송 실패·재시도 시 동작을 검증한다.
- [ ] 브리핑 이력이 실제 수신 전에 확정되는지 조사하고, 실패 시 재전송·누락 정책을 Issue에서 결정한다.
- [ ] 현재 전체 DB 검색의 결과량·오래된 기사 노출을 평가하고, 필요할 때 기간·개수 제한을 별도 범위로 설계한다.

생활 기록에서 할 일:

- [ ] 네 schema, 항목 추가·목록·삭제, 같은 날짜 갱신, 상대 날짜·과거 날짜, 음주 환산과 구조화 저장을 검증한다.
- [ ] Telegram에서 단답·묶음·부분 답변·부정 답변·날짜 버튼이 올바른 항목과 날짜로 저장되는지 확인한다.
- [ ] 예약 질문·재알림·후속 누락 질문·키보드 제거·발송 실패 경로와 중복 질문을 검증한다.
- [ ] 최근 7일·30일 코멘트의 근거와 톤을 확인하고, 기록 없음과 실제 안 함을 혼동하지 않는지 점검한다.
- [ ] 통계의 분모·단위·기간 경계를 문서화한다. 기록일 기준 수행 비율과 전체 기간 기준 수행률을 구분한다.
- [ ] 항목 삭제의 기록 영향과 개별 기록 수정/삭제 필요성을 확인한다. 새 삭제 기능은 실제 요구가 있으면 별도 승인한다.

**산출물:** AC별 현재 기능 검증표, 결함별 작은 수정 Issue/PR, 뉴스·기록 운영 관찰 결과.

**완료 조건:** 위 경로의 PASS 또는 알려진 제약을 기록했고, 사용자 데이터를 훼손하거나 저장 성공을 잘못 알리는 결함이 해결되었다.
권장 실사용 표본은 연속 7일이며 세 브리핑 시각·tracking 예약과 재알림을 포함한다. 최종 기간·허용 수준은 Human이 Issue에서 승인한다.

**Issue 후보:** `R1 뉴스 생성·전달·재시도 검증과 개선`, `R2 생활 기록 대화·통계·알림 검증과 개선`.
기존 코드에 있는 기능은 새 기능으로 재구현하지 않는다.

## 단계 2. Watch 조건 관리

**목적:** 사용자가 어떤 변화를 알고 싶은지 명확히 등록하고 조절할 수 있게 한다.

해야 할 일:

- [ ] 실제 관심 조건 예시와 제외할 조건을 Human과 정한다. 예: 특정 기업의 특정 기술 관련 중요한 변화.
- [ ] 등록·목록·조회·수정·일시 중지/재개·삭제 중 MVP 범위를 결정한다. 최소한 등록·조회·중지/삭제는 가능해야 한다.
- [ ] 자연어 조건을 어떻게 확인할지, 조건명·설명·관심 주제·활성 여부를 어떻게 저장할지 Issue에 설계한다.
- [ ] `msalt/storage.py` 패턴을 활용한 데이터 모델과 기존 DB를 보존하는 마이그레이션을 설계·구현한다.
- [ ] `msalt/watch/` 도메인과 CLI, Telegram 스킬을 추가하고 `msalt/cli.py`에 진입점을 연결한다.
- [ ] 빈 조건·중복 이름·잘못된 ID·비활성 조건·재시작 후 유지·스키마 업그레이드를 테스트한다.

**예상 변경 영역:** `msalt/storage.py`, `msalt/cli.py`, 새 `msalt/watch/`, 새 스킬, `tests/msalt/watch/`.
정확한 테이블·명령 이름은 승인 설계에서 확정한다.

**산출물:** Watch 관리 기능·데이터 마이그레이션·Telegram 등록/관리 사용 예시.

**완료 조건:** 조건 등록 후 조회·관리·비활성화가 가능하고 재시작 후 유지되며, 기존 뉴스·생활 데이터가 보존된다.
이 단계만으로 능동 뉴스 알림이 제공된다고 소개하지 않는다.

**Issue 후보:** `R3 Watch 조건 관리와 Telegram 진입점`.

## 단계 3. Watch 평가와 능동 알림

**목적:** 브리핑 시간 사이에도 새 기사에서 중요한 변화만 받아본다.

해야 할 일:

- [ ] 현재 브리핑 직전 수집과 별개로 새 기사를 확인할 주기·작업 실행 방식을 정한다. 주기 수치는 비용·시의성을 보고 승인한다.
- [ ] 새 기사 판정 기준과 첫 Watch 등록 시 기존 기사 처리, 평가 실패·재시작 후 재처리 정책을 정한다.
- [ ] 조건별 값싼 후보 필터 후 필요한 기사만 LLM 평가하는 방식을 우선 검토하고, 관련성·중요도·근거와 판단 실패를 구분한다.
- [ ] 기사와 Watch의 관계, 평가 상태·시각, 알림 대기·성공·실패 이력과 중복 방지 키를 설계한다.
- [ ] 발송 빈도·묶음 전송·일시 중지·한도와 중복 알림 정책을 정한다. 한 기사가 여러 조건에 걸릴 때 UX도 정한다.
- [ ] 기사 제목·알림 이유·원문을 전달하고, 발송 성공·실패를 구분해 저장한다. 발송 후 상태 저장 실패 등 불확실한 결과의 처리도 정한다.
- [ ] LLM timeout·검색 실패·Telegram 실패가 기존 수집·브리핑·기록을 중단시키지 않도록 격리한다.
- [ ] 처리량·API 한도·실행 시간·메모리·비용 관찰과 정지 수단을 추가한다.
- [ ] 관련/무관 기사, 같은 URL, 여러 Watch, inactive, 재시작, 동시 실행, 재시도·시간 경계를 독립 검증한다.

**예상 변경 영역:** 새 Watch 평가·dispatcher, `msalt/news/collector.py` 또는 저장 기사 조회 연결,
`msalt/storage.py`, CLI·스킬, `deploy/`, Watch·뉴스 회귀 테스트.
기존 뉴스 브리핑 이력과 Watch 알림 이력은 목적을 구분한다.

**산출물:** 조건별 새 기사 탐지·알림, 실행/발송 이력, 운영 관찰 보고서.

**완료 조건:** Human이 관련/무관으로 확인한 기사 표본을 통해 결과를 설명할 수 있고,
중복·실패·중지 경로를 검증했으며 실사용에서 유용성과 알림 부담을 수용했다.
Telegram 발송을 무조건 exactly-once로 보장한다고 주장하지 않는다.

**Issue 후보:** `R4 Watch 신규 기사 평가와 재처리`, `R5 Watch 알림·중복 방지·운영 제어`.
R4 검증은 발송 없는 평가로 시작하고, R5에서 실제 알림을 승인된 대상에 연결한다.

## 단계 4. 생활 기록 주간 Review

**목적:** 기록할 때의 짧은 코멘트를 넘어, 한 주의 생활을 근거와 함께 돌아본다.

해야 할 일:

- [ ] 집계 기간·KST 경계·발송 요일/시각·사용자가 원하는 출력 길이를 정한다.
- [ ] 기록일 수·누락일 수·duration 평균/합계·quantity 합계·boolean 수행/미수행을 공통 집계한다.
- [ ] 누락을 0 또는 미수행으로 처리하지 않는다. 비교할 전주 데이터가 부족하면 부족함을 표시한다.
- [ ] 자유 메모와 민감한 기록의 포함 범위, 7일·30일 기존 코멘트와 중복되지 않는 역할을 정한다.
- [ ] 먼저 결정적인 수치 집계와 텍스트 보고서를 만들고, 필요한 설명만 LLM으로 보완한다. 근거 없는 원인·건강 판단을 생성하지 않는다.
- [ ] 수동 생성·조회 진입점을 만들고, 정기 생성·전송과 같은 기간 중복 발송 방지를 연결한다.
- [ ] 빈 DB·일부 기록·기간 경계·전주 없음·사용자 항목 변경·LLM/전송 실패·재생성을 검증한다.

**예상 변경 영역:** `msalt/tracking/records.py`, 새 Review 모듈/스킬, `msalt/storage.py`,
`msalt/cli.py`, `msalt/workspace/cron/jobs.json`, Review 테스트.

**산출물:** 생활 주간 보고서·집계 규칙·예약 전송·사용 예시.

**완료 조건:** DB 원본으로 각 수치와 기간을 재현할 수 있고, 누락을 사실과 구분하며,
최소 한 집계 주기를 실제 사용해 Human이 내용·길이·시각을 수용했다.

**Issue 후보:** `R6 생활 Review 집계와 수동 보고`, `R7 생활 Review 정기 전송과 전달 이력`.

## 단계 5. 뉴스·Watch·생활 통합 Review

**목적:** 따로 받은 메시지를 더 늘리지 않고, 한 주의 관심 변화와 생활을 한 보고서로 정리한다.

해야 할 일:

- [ ] 생활 Review에 추가할 뉴스·Watch 섹션과 길이를 정한다. 정기 브리핑 원문을 반복하지 않는다.
- [ ] Watch별 주요 변화·알림 수·중요 기사 링크·중복 및 평가 실패를 집계한다.
- [ ] 관심 조건이 없거나 해당 기간 새 기사가 없을 때의 출력과 개인 관심사 반영 범위를 정한다.
- [ ] 각 섹션을 따로 집계해 일부 데이터·외부 호출이 실패해도 전체 보고가 사라지지 않게 한다.
- [ ] 기존 생활 Review의 예약을 확장할지 대체할지 정하고, 별도 알림이 중복되지 않게 한다.
- [ ] 뉴스와 생활 사이의 인과관계를 추측하지 않으며, 사실·사용자 판단·제안을 구분한다.
- [ ] 빈 Watch·빈 기록·일부 실패·긴 출력·동일 주 재생성·기간 경계를 검증한다.

**산출물:** 근거 링크와 생활 수치가 있는 통합 주간 보고, 단일 예약·전송 경험.

**완료 조건:** Human이 한 보고서에서 자신의 관심 변화와 생활을 파악하고,
별도 메시지 수나 읽기 부담이 불필요하게 늘지 않았다고 판단한다.

**Issue 후보:** `R8 Watch·뉴스·생활 통합 주간 Review`.

## 단계 6. 실사용 기반 개인화와 회고

**목적:** 기능을 늘리는 대신 실제로 유용했던 결과를 기준으로 개선한다.

해야 할 일:

- [ ] Watch의 유용한 알림·무관 알림·놓친 기사, Review의 읽기 부담·유용성, 기록 입력의 마찰을 Human 사용 기록으로 수집한다.
- [ ] 이미 확인 가능한 로그·통계부터 활용한다. 관찰 수단이 없는 지표는 확인했다고 기록하지 않는다.
- [ ] 필요가 확인된 경우에만 조건 수정 UX·알림 한도·조용한 시간·요약 길이·일시 중지 개선을 별도 Issue로 만든다.
- [ ] 잘못된 기록을 고치는 경로와 사용자 선호·프로필 변경 흐름을 검토한다. 일별 데이터를 SOUL/USER에 누적하지 않는다.
- [ ] 기본 설정 대비 개선 효과를 비교하고, 호출 비용·메모리·장애 대응이 단일 RPi/OCI 호스트 운영 범위에 맞는지 확인한다. 양쪽에 영향을 주는 변경은 저메모리 RPi에서의 영향도 검증하거나 미검증 한계를 기록한다.
- [ ] 각 완료 Issue의 기대·실제·결정·후속 작업을 회고하고 AX Notes 소재를 사실 근거와 함께 정리한다.

**산출물:** 실제 사용 근거가 있는 개선 Issue, 제품 회고, 공개 전 검토 가능한 AX Notes 소재.

**완료 조건:** Human이 브리핑·기록·Watch·Review를 계속 사용할 가치가 있다고 판단하고,
기능을 추가·조정·중지할 근거를 남겼다. 이후에도 새로운 개선은 작은 Issue로 반복한다.

**Issue 후보:** `R9 실사용 결과에 따른 알림·Review 조정`. 미리 임의 설정 UI를 전부 구현하지 않고 관찰로 범위를 결정한다.
