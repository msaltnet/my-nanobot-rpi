# my-nanobot-rpi PRD

최종 갱신: 2026-10-05.
공개 프로젝트의 제품 목표·현재 기능·확장 요구사항을 정의한다. 현재 구현은 저장소 코드와 스킬 기준이다.
Watch·정기 Review는 개발 예정이며, 이 문서가 개별 기능의 상세 설계 승인이나 구현 완료를 의미하지 않는다.

## 1. 제품 목표와 사용자

텔레그램에서 경제 정보를 받고 생활을 기록하며, 중요한 변화와 누적 패턴을 돌아볼 수 있는 **개인용 AI 비서**를 만든다.
최종 경험은 `정보 수집 → 필요한 변화 알림 → 생활 기록 → 주기적 돌아보기 → 사용자 판단`이다.
정보 사이트와 기록 앱을 오가는 부담을 줄이고, 계속 사용할 만큼 유용한 결과를 제공한다.

각 사용자는 공개 코드를 자신의 RPi 또는 OCI Cloud Instance에 설치한다. 한 배포는 개인 사용자 한 명을 중심으로 운영한다.
유지관리자의 서버·계정·설치 경로는 공통 요구사항이 아니다. 기본 언어·일정은 한국어와 Asia/Seoul이며 개인 선호·항목을 관리한다.
일정·시간대 변경은 현재 설정이 적용되는 범위와 추가 개발이 필요한 범위를 구분해 안내한다.

| 필요 | 문제 | 목표 경험 |
|------|------|-----------|
| 경제 흐름 파악 | 분산된 소스와 중복 기사 | 근거 링크가 있는 짧은 정기 브리핑 |
| 관심 변화 확인 | 브리핑 사이 직접 확인 필요 | 관심 조건에 맞는 새 변화 알림 |
| 생활 기록 유지 | 입력·날짜·항목 선택 부담 | 자연어·답변 버튼으로 기록하고 갱신 |
| 누적 패턴 확인 | 개별 기록만으로 돌아보기 어려움 | 누락을 구분한 주기적 Review |
| 직접 운영 | 설치·설정·복구의 환경 차이 | RPi/OCI 공통 절차와 환경별 안내 |

## 2. 기능 범위와 상태

| ID | 기능 | 상태 |
|----|------|------|
| F1 | 정기 경제 브리핑 | 현재 구현 |
| F2 | 대화형 뉴스 조회 | 현재 구현 |
| F3 | 생활 기록·통계·즉시 코멘트 | 현재 구현 |
| F4 | 능동 질문·누락 후속 확인 | 현재 구현 |
| F5 | 관심 조건 기반 Watch | 개발 예정 |
| F6 | 생활·뉴스·Watch 주기적 Review | 개발 예정 |

현재 구현은 코드 존재를 뜻하며 운영 검증 완료를 뜻하지 않는다. 안정화도 로드맵에 포함한다.
인프라·메모리·진단은 제품 기능을 지원하는 기반으로 구분한다.

## 3. 현재 기능 요구사항

### F1. 경제 뉴스 브리핑

- 일반 RSS 7개, 공식 기관 피드 3개, Tavily/Brave 검색, HTML/sitemap 보완 경로로 수집한다. 소스는 설정 파일로 관리한다.
- 국내·해외·정책/지표별 한국어 요약과 원문 링크를 제공한다.
- 기본 예약은 07:00·14:00·20:00 KST다. 수동 수집·브리핑 요청도 제공한다.
- URL 중복, 발행 시각, 이미 브리핑한 URL 이력으로 기사 선택을 제한한다.
- 수집 경로 실패를 다른 경로와 격리한다. 빈 결과·외부 호출 실패를 성공으로 꾸미지 않는다.

**수용 기준:** 세 예약과 수동 흐름, 출처·기간·중복 처리를 검증한다. 생성 성공과 Telegram 수신 성공을 구분한다.
현재 브리핑 이력은 생성 과정에서 기록되므로 발송 실패 시 재전송·누락 정책은 안정화 Issue에서 보완한다.

### F2. 대화형 뉴스 조회

- 뉴스 스킬에서 수집·브리핑·키워드 검색을 실행한다.
- 현재 검색은 DB에 저장된 기사 제목·요약을 대상으로 원문 링크를 반환한다.
- 검색 결과 없음과 검색 범위·최신성 한계를 안내한다.

**수용 기준:** 저장 기사에 맞는 결과와 링크를 제공한다. 기간 제한 검색·주간 통합 보고서·항상 최신 기사 자동 검색을 현재 전용 기능으로 소개하지 않는다.

### F3. 생활 기록·통계·즉시 코멘트

- 기본 항목은 수면(duration), 음주(quantity, 순알코올 g), 영어공부(boolean)다.
- freetext/duration/quantity/boolean 형식으로 사용자 항목을 추가·조회·삭제한다. 자연어 항목 추가는 형식·단위·시각을 확인한 뒤 등록한다.
- 자연어 기록의 항목·날짜·값을 결정해 저장하고 같은 항목·날짜의 재입력은 갱신한다.
- 단답은 직전 질문의 항목·대상 날짜를 참고한다. 사용자가 명시한 날짜·항목이 우선하고 확정할 수 없으면 필요한 정보를 묻는다.
- 음주 종류·양·용량·도수를 구조화하고 순알코올 g으로 환산한다. 기본값으로 추정했다면 짧게 설명한다.
- 평균·합계·수행 비율·최근 메모와 최근 7일·30일 데이터 기반 패턴 코멘트를 제공한다.
- 저장 실패를 기록 완료로 알리거나 파일·메모리에 대신 저장하지 않는다.

**수용 기준:** 값·단위·대상 날짜를 DB로 확인하고 재입력 후 중복 행이 늘지 않는다. 집계 기간·분모·추정 기준을 설명할 수 있다.
현재 boolean 비율은 기록 수를 분모로 하므로 전체 기간 수행률과 구분한다. 항목 삭제와 관련 기록 삭제의 관계를 안내한다.
개별 기록 삭제·항목 수정 전용 UX는 별도 개발 여부를 결정한다.

### F4. 능동 질문·누락 후속 확인

- 30분 디스패처가 항목별 예약 질문을 처리한다. 미응답 pending 항목은 기본 09:00·14:00·20:00 KST에 재알림한다.
- 여러 질문을 묶고 schema별 날짜·항목을 포함한 답변 키보드를 제공한다.
- 여러 항목 답변은 항목별로 저장하고 부분 답변은 답한 항목만 처리한다.
- 기록 직후 최근 누락 항목을 후속 질문으로 제시하고, 누락이 없으면 키보드를 제거한다.

**수용 기준:** 예약·재알림·단답·부분 저장·키보드 제거와 실제 대상 날짜를 Telegram 흐름으로 검증한다.
알림이 응답이나 완전한 기록을 보장한다고 주장하지 않는다. 알림 피로를 실사용 수용 기준에 포함한다.

## 4. 개발 예정 요구사항

### F5. 관심 조건 기반 Watch

브리핑 사이에도 사용자가 알고 싶은 새 변화를 알려준다.

- 조건 등록·조회·중지/삭제가 가능해야 한다. 수정·재개 UX의 MVP 범위는 설계 시 정한다.
- 새 기사 판정, 최초 등록 시 기존 기사 취급, 실패·재시작 후 재처리 정책을 정한다.
- 관련성·중요도를 평가하고 알림 이유·원문을 제공한다.
- 동일 기사·다중 조건 중복, 알림 빈도·비용·중지 수단을 함께 설계한다.
- 평가·발송 실패가 기존 수집·브리핑·기록을 중단시키지 않아야 한다.

**수용 기준:** 관련/무관 기사 표본으로 결과를 설명하고 중복·중지·오류·재시작을 검증한다.
Human이 유용성과 알림 부담을 수용한다. 정확도 목표·한도·주기는 개별 Issue에서 승인한다.

### F6. 주기적 Review

먼저 생활 주간 Review를 제공하고 이후 뉴스·Watch·생활을 통합한다.

- 기간·시간대·발송 시각을 명시하고 수동 생성·예약 전송을 제공한다.
- 기록일·누락일·schema별 집계와 가능한 전주 비교를 근거 데이터와 함께 제공한다.
- 기록 없음과 실제 0·미수행을 구분하고 근거 부족·일부 실패를 드러낸다.
- 통합 Review는 주요 관심 변화·원문·Watch 결과·생활 수치를 요약하며 기존 알림을 반복하지 않는다.
- 근거 없는 원인·인과관계·건강/투자 판단을 만들지 않는다.

**수용 기준:** 수치·기간·링크를 원본으로 재현하고 빈 데이터·부분 실패·동일 기간 재생성을 검증한다.
최소 한 집계 주기를 사용해 Human이 내용·길이·시각을 수용한다.

## 5. 공통 제품·운영 요구사항

- **공개 배포:** RPi/OCI 단일 Linux 호스트를 지원한다. 특정 서버·SSH 별칭·계정·설치 경로를 필수로 지정하지 않는다.
- **개인화:** SOUL/USER는 지속적인 선호·설정, SQLite는 생활·뉴스 데이터를 관리한다. 일별 기록을 프로필에 누적하지 않는다.
- **신뢰성:** 성공·실패·미검증을 구분하고 재시도·데이터 보존·마이그레이션·백업/복구를 문서화한다.
- **사용 부담:** 알림 수보다 유용성·간결성·입력 마찰을 우선한다. 훈계하거나 불확실한 해석을 단정하지 않는다.
- **자원·비용:** 저메모리 환경을 고려해 API 호출·메모리·처리 시간을 관찰한다. 측정 없이 고정 비용·응답 시간을 약속하지 않는다.
- **데이터·접근:** 개인 중심 Telegram allowlist를 설정한다. 비밀값·개인 기록·실제 서버 정보는 공개 저장소에 올리지 않는다.
- **재현성:** 공통 요구 버전·설치·기동·업데이트·진단과 환경 차이를 안내한다. 실제 서버 상태는 운영자별 비공개 기록으로 관리한다.

## 6. Non-goals

- 다중 사용자 SaaS, 계정·결제 서비스.
- 투자 권유·매매 추천·자동 매매·실시간 시세/체결 시스템.
- 별도 모바일/웹 앱, 공개 뉴스레터·광고 발송.
- 이번 로드맵에서의 음성·새 채널·로컬 LLM·대형 분산 인프라.

새 소스·차트·음성 등은 실제 문제가 확인되면 별도 Issue로 검토한다. 클라우드 배포는 제외 대상이 아니다.

## 7. 성공 판단과 검증

| 관찰 항목 | 확인 방법 | 수용 판단 |
|-----------|-----------|-----------|
| 브리핑 누락·중복·근거 | 생성 로그·Telegram 수신·URL/발행 시각 | 승인된 예약·기사 선택·실패 정책 충족 |
| 기록 날짜·값·수정 | 대화 표본과 SQLite 대조 | 저장 완료 응답과 원본 일치 |
| 알림 유용성·부담 | 유용/무관/중복/누락에 대한 Human 관찰 | 계속 사용할 수 있는 경험 |
| Review 재현성·부담 | 집계 원본·한 주기 사용 | 근거가 맞고 한 번에 돌아볼 수 있음 |
| 비용·자원·실패 | 확인 가능한 API 이용량·호스트 로그 | 해당 환경의 승인 예산·운영 범위 충족 |
| 유지 사용 가치 | Dogfooding Notes | Human의 명시적 수용 |

정량 임계값·표본·기간은 Issue에서 정한다. 과거의 30일 무중단·5초 응답·고정 월 비용 목표를 달성 수치로 기록하지 않는다.
수집하지 못한 지표는 미측정으로 표시한다.

## 8. 로드맵과 개발 수용 절차

운영 준비 → 기존 기능 안정화 → Watch 관리 → Watch 알림 → 생활 Review → 통합 Review → 실사용 개선.
단계별 할 일·Issue 후보·완료 조건은 [구현 로드맵](implementation-roadmap.md)을 따른다.

Issue는 Open/Planning/Ready for Implementation으로 관리하고 Human 설계 승인 후 구현한다.
독립 테스트·리뷰 PASS 후 PR을 생성하며 승인된 후보 배포·실사용·Human PR 검토와 최종 수용 후 Merge한다.
구현 문제는 Ready에서 수정하고 설계 변경은 Planning으로 돌아간다. 일반 설치 사용자에게 개발 보드 참여를 요구하지 않는다.

## 9. 제품·설계 결정

| 결정 | 이유 |
|------|------|
| nanobot 서브모듈 + msalt | 프레임워크 재사용과 개인 도메인 분리 |
| Telegram 중심 개인 배포 | 기존 대화 인터페이스에서 정보·기록 연결 |
| SQLite·파일 워크스페이스 | 단일 호스트 데이터 관리·백업/복구 |
| RPi/OCI 공통 배포 | 사용자의 하드웨어·클라우드 선택 허용 |
| 스킬 + Python CLI/도구 | 자연어 처리와 결정적인 저장·집계 구분 |
| Watch → Review | 필요한 변화 알림·누적 돌아보기로 가치 확대 |
| 실사용 후 수용 | 테스트 외에 알림 피로·유용성·운영성 확인 |
