# 주요 기능과 프로젝트 방향

`my-nanobot-rpi`는 텔레그램에서 경제 정보를 받아보고 생활을 기록하는 **1인용 개인 AI 비서**다.
현재는 OCI에서 운영하고, RPi에도 같은 코드를 배포할 수 있다.
공개 프로젝트로서 RPi/OCI 배포를 모두 지원한다. 유지관리자의 현재 OCI 운영은 한 사례이며,
사용자의 서버·사용자명·설치 경로를 고정하는 제품 요구사항이 아니다.
2026-10-05 기준 코드·설정과 사용자가 제공한 운영안을 바탕으로 현재 기능과 앞으로의 방향을 정리한다.
아래 확장 후보는 구현 완료나 Human 설계 승인을 뜻하지 않는다. 각 후보는 Open Issue → Planning → 승인 절차를 거친다.

## 현재 주요 기능

앱의 현재 도메인은 **경제 뉴스**와 **생활 기록** 두 가지다. 사용자 경험으로 나누면 다음 네 기능을 제공한다.

| 기능 | 사용자가 얻는 가치 | 현재 구현 / 근거 |
|------|--------------------|------------------|
| 정기 경제 브리핑 | 분산된 경제 소식을 짧게 읽는다 | 07:00·14:00·20:00 KST, 국내·해외·정책/지표 요약과 원문, RSS·공식 피드·검색·HTML 수집, 브리핑 중복 제외 (`msalt/news/`) |
| 대화형 뉴스 조회 | 궁금한 주제를 텔레그램으로 물어본다 | 뉴스 스킬, 수집 기사 키워드 검색·대화형 요청 (`msalt/skills/news/`, `msalt/news/cli.py`) |
| 사용자 정의 생활 기록·통계 | 별도 앱을 열지 않고 자신의 생활을 남긴다 | 수면·음주·영어공부 기본 항목, 4가지 schema, 자연어 날짜·값 처리, 기록 갱신, 평균·합계·수행률, 순알코올 환산 (`msalt/tracking/`) |
| 능동 질문·누락 후속 확인 | 잊은 기록을 대화로 보완한다 | 30분 디스패처, 예약 질문, 미응답 재알림, 답변 키보드, 기록 후 누락 질문 (`dispatcher.py`, `reply_tool.py`) |

### 세부 기능 확인

- **뉴스 수집·브리핑**: 일반 RSS·공식 기관 피드·Tavily/Brave·HTML/sitemap 보완 경로, 수집 경로별 실패 격리, URL 중복 제거, 발행 시각 필터, 브리핑한 URL 이력 제외, 수동 수집·브리핑 실행.
- **뉴스 조회**: 저장된 기사의 제목·요약 키워드 검색과 원문 링크, 뉴스 스킬을 통한 대화형 호출. 검색은 현재 저장 기사 전체를 대상으로 한다. 전용 기간 검색·주간 통합 보고서는 별도로 구현되어 있지 않다.
- **항목·기록**: 항목 추가·목록·삭제, 사용자 확인 후 새 항목 등록, 4가지 schema, 날짜별 기록 upsert, 음주 종류·용량·도수의 구조화 저장과 순알코올 환산.
- **대화 처리**: 직전 질문의 항목·대상 날짜를 이용한 단답 처리 지침, 여러 항목 답변의 개별 저장, 부분 답변 처리, 날짜가 포함된 버튼 답변과 boolean 부정 기록.
- **통계·즉시 피드백**: 항목별 기간 조회·평균·합계·수행 비율·최근 메모, 기록 직후 최근 7일·30일 패턴 코멘트. 현재 수행 비율은 기록된 항목 수를 분모로 계산하므로 전체 기간의 수행률과 구분한다.
- **알림·후속 질문**: 예약 질문·미응답 재알림·여러 항목 묶음 발송·schema별 답변 키보드·최근 누락 항목 후속 질문·누락이 없을 때 키보드 제거.

이 목록은 코드와 스킬에 존재하는 주요 경로를 정리한 것이며, 운영 환경에서 모든 경로의 실사용 검증이 끝났다는 뜻은 아니다.
단답·묶음 답변의 자연어 해석은 에이전트와 스킬 지침에 의존하므로 실제 Telegram 흐름까지 확인해야 한다.

### 공통 기반과 운영 기능

제품 기능을 지원하는 기반으로 nanobot의 에이전트·메모리·dream, SOUL/USER 템플릿과 스킬·크론 동기화,
OpenAI Responses 호환 처리, 기존 프로필 기록 아카이브와 설정 정비, SQLite 마이그레이션을 사용한다.
`doctor`는 환경 변수·설정·워크스페이스·크론과 뉴스 소스 연결을 점검한다.
systemd 서비스·tracking 타이머·Telegram 타임아웃 워치독·journald가 운영을 지원한다.
이 항목들은 앱의 새로운 사용자 기능으로 중복 집계하지 않는다.

인프라는 기능과 구분한다. nanobot은 대화·스킬·크론·메모리를 제공하고, msalt는 도메인 로직을 제공한다.
SQLite와 워크스페이스 파일을 단일 Linux 호스트에서 관리한다. 실행 사양과 구조는 [README](../README.md)에 정리되어 있다.

## 최종 방향

정보를 전달하고 기록을 저장하는 비서에서, **중요한 변화를 먼저 알려주고 자신의 생활을 돌아보도록 돕는 개인 비서**로 발전시킨다.
중심 경험은 `정보 수집 → 필요한 변화 알림 → 생활 기록 → 주기적 돌아보기 → 사용자 판단`이다.
더 많은 메시지를 보내는 것보다 사용자가 계속 쓸 만큼 유용한지, 입력과 확인의 부담이 줄었는지가 중요하다.

현재 네 경험에 다음 두 확장 후보를 더하면 여섯 기능 영역으로 개발을 구분할 수 있다.
첨부안의 Watch·주간 Review 사례를 방향으로 정리한 것이며, 구체적 인터페이스·우선순위·수치는 Issue에서 승인받는다.

| 확장 후보 | 목표 경험 | 아직 정해야 할 것 |
|-----------|-----------|--------------------|
| 관심 조건 기반 Watch | 정기 브리핑 사이에도 자신에게 중요한 변화만 알림 | 조건 등록 UX, 관련성·중요도 판단, 중복·알림 피로 제어, 호출 비용, 오류 격리 |
| 주기적 Review | 뉴스 관심사와 누적 생활 기록을 요약해 자신의 패턴을 돌아봄 | 집계 기간·형식·일정, 근거 링크·데이터, 누락 표현, 유용성·비용 기준 |

Watch 명령, 데이터 테이블, threshold, 평가 방식은 현재 구현되어 있다고 가정하지 않는다.
주기적 Review 역시 현재 항목 통계와 다른 미래 기능이며, 과거 기록을 근거 없이 해석하지 않도록 설계한다.

## 제품 판단 원칙

- 개인 사용자 한 명의 실제 필요를 우선하고, 텔레그램 중심 UX를 유지한다.
- 능동 알림은 관련성·시의성·중복 방지·빈도와 끄기/조정 경험까지 함께 검토한다.
- 뉴스는 근거와 원문을 제시한다. 투자 권유·자동 매매는 목표에 포함하지 않는다.
- 생활 기록은 훈계 없이 받아들이고, 실제 저장 실패를 성공으로 알리지 않는다.
- 클라우드 LLM을 사용하되 단일 호스트의 메모리·호출 비용·운영 복잡성에 맞게 설계한다.
- SQLite 데이터와 개인 컨텍스트를 보존하고, 기능마다 별도 대형 인프라를 먼저 만들지 않는다.

다중 사용자 SaaS, 별도 모바일/웹 앱, 실시간 시세·자동 매매는 현재 개발 방향에 포함하지 않는다.
새 채널·음성·시각화·소스 추가는 실제 사용 문제와 효과가 확인되면 별도 후보로 검토한다.
비용·응답 시간·무중단 목표는 실제 측정과 Issue별 수용 기준으로 관리하며, 과거 목표를 현재 달성 수치로 인용하지 않는다.

## 권장 개발 순서와 성공 근거

단계별 할 일·Issue 후보·검증·완료 조건은 [구현 로드맵](implementation-roadmap.md)에 정리한다.
순서는 **운영 준비 → 현재 기능 안정화 → Watch 관리 → Watch 알림 → 생활 Review → 통합 Review → 실사용 개선**이다.

위 순서는 제안이며 승인된 구현 큐가 아니다. 구체 작업은 Projects의 Ready Issue에서만 가져온다.
성공은 브리핑·알림 누락과 중복, 기록 성공·수정 가능성, API 실패·비용, 운영 자원,
그리고 Human의 `계속 사용하겠다`는 판단을 함께 보고 정한다. 달성하지 않은 지표를 성공으로 기록하지 않는다.

## 개발 자체에서 얻을 결과

제품 개발은 [Agentic Workflow](development/agentic-workflow.md)로 운영한다.
Issue 설계, 독립 테스트·리뷰, 후보 배포, Dogfooding, 최종 수용을 연결해 작은 개선을 반복한다.
회고는 다음 제품 Issue와 Project Note로 남기고, 실제 근거가 있는 경험만 AX Notes 소재로 정리한다.
AX Notes 작성은 제품 기능과 별개의 지식화 활동이며 자동 외부 게시를 의미하지 않는다.

[PRD](msalt-prd.md)는 제품 요구사항, [TRD](msalt-trd.md)는 현재 기술 구조와 확장 기준을 정의한다.
실행 환경은 README·배포 가이드, 단계별 작업은 로드맵, 기능별 구현 계약은 Human이 승인한 최신 Issue 본문을 기준으로 한다.
